> I was going to give this as a talk for my larger product team at work, but decided to just write it down instead because I don't know how useful this will be and I don't think going over a bunch of code examples on a slideshow would be helpful for illustrating my point.

Well, AI coding has kind of taken over in the past few months, it's really unavoidable.  It's also a really good productivity booster... for the most part.

What I've found is that, while we can write code faster, reviewing code has become a huge bottleneck.

Of course, we can get rid of this bottleneck by having AI review the code as well, which we do, but I personally don't think that get's rid of the bottleneck,
it just pushes the review from the engineers job to the customers job when they find a bug caused by:

1. An unclear prompt...
2. Leading to an assumption by the agent...
3. Writing code implementing this assumed behavior or restriction...
4. With good test coverage and clear documentation...
5. That passes AI code reviews because it works...
6. That has not actually been looked at by the engineer to confirm it didn't do anything weird.

This sort of situation is entirely avoidable by simply *reading the code* the agent writes... except reading code is really hard!
Part of what makes code easier to understand is writing code and being forced to understand the surrounding context of the code you're writing, but as we move towards less of the writing part, the reading part becomes increasingly more difficult.  To add to that difficulty... AI writes a lot of code very quickly, and while my team has found it incredibly useful for getting long standing and important refactors and fixes out of the way, the reason why those issues were long standing is because they would require a huge PR, and we still want to be able to review that big PR!

So, if we work backwards, what we want is some sort of tool, process, mindset, etc that makes reviewing PR's easier, makes PR's smaller, makes agents assume less from an unclear prompt, or makes prompts more clear.

And we actually do have a solution for that, it's the programming language you use! Even though this post is about Rust, your programming language of choice offers a lot of tools to encode your intentions and guard rails into the code you or someone else (someone here being more of a something... still huanted by seeing an agents comment addressing me as a *human* programmer...) will have to abide by.  

The tools available don't just let you define intention better leading to more correct code, they let you do it in such a way that code can be written even faster due to tightening the feedback cycle.  Before I actually go into the tools and how/why we should use them (and ultimately why I think Rust is our best language available), let's go over those feedback loops:

* Coding -> Compiling -> Testing -> Running -> Releasing
    * This is our slowest feedback loop, and the one we really don't want to see an error in.  If we see an error here, it means a customer spotted it (which makes us look bad and, as a customer myself, is very annoying) or will spot it.  If we see an error here, we have to go through a bit of exploratory work to figure out what actually caused it, which requires a lot of code exploration usually.  It also means to fix the error, we have to go through the whole release process again.
* Coding -> Compiling -> Testing -> Running
    * This is your local debugging feedback loop.  It's very open ended which is good, but ideally if you're discovering a bug here, you're going to wish you discovered it earlier.  It is still a relatively slow feedback loop as each bug you find requires both running the code (entailing any setup cost required to do so) and exploring well enough to find a bug.  When we do find a bug, it also requires a similar amount of code exploration to narrow down the issue.
* Coding -> Compiling -> Testing
    * We love this feedback loop, it's reasonably quick (if you wrote your tests to run very quickly (you should write your tests to run very quickly )) and a very focused guardrail for specific behaviors and constraints.  If a test fails, there's usually going to be a pretty narrow scope of the code that can cause it to fail.  The only issue is that tests tend to grow large and complex as the feature they are testing grow, so writing/maintaining/***reading*** them becomes a pain.
* Coding -> Compiling
    * This is the loop we love.  This is the loop your agents love.  When you see a bug here, you don't have to do any extra work to figure out where or what is causing the bug, because the compiler will tell you, and the code at issue is usually going to be the same code generating the compiler error, if it's not, the compiler will usually be able to tell you what code is the problem.

The rest of this post is going to be discussing tools that let us move errors from the end of the feedback chain, all the way to the beginning, tools that let us write intention and restriction as code and not as a prompt.  The tools are simple and we've had them this whole time.  Just because are computers are now able to read and act on plain text much better than before, it doesn't mean they stopped being computers that can read and act on programming languages determinstically, so we should really be using *type systems and static analysis* to better guide our agents.

# Type Systems and Static Analysis

Our type systems let us turn our code from a process into a contract, and static analyzers + extensible static analysis systems let us extend our base languages type systems and designs with our own extra rules and restrictions for feedback at compile time.  

## C# (Basic)

Let's look at this C# method and try to figure out what the signature is telling the reader, whether that's us or an agent:

```C#
public uint DoThing(string id, uint value);
```

Well... here's what we know:
* This is a method, everything in C# is a method on something.
    * *C# 9 added top level statements in main... fucntions here are still static methods on a compiler generated class iirc (I'm not looking this up, assume it to be true :))*
* It returns a non negative int.
* It takes a string id argument and some non negative int value argument.
* It allegedly *does thing*.
* It is public, it can be called from a higher context.
* It's not asyncronous.

Now what are the things we don't know from looking at it:
* What exactly is id, what id's are okay? Is it correct to put any string there?
* What values are okay, is anything okay?
* Is this method going to modify `this` in someway?
    * It could modify it.
    * It could also just read information from it.
    * If it's a struct we could mark it `readonly`, but not for classes.
* Can this method fail? Does it throw exceptions? What exceptions can it throw?

So what we have here is a method that uses it's name, and argument names, to tell us it's intention, to **do thing**, but it hasn't communicated what restrictions we have when doing thing.  We know we can do it, but we don't know how, when, or why.

Is this valid?

```C#
foo.DoThing("some random id", 1000);
```

Maybe... so let's use some simple typing to start turning this into a contract we have to follow:

```C#
public class Cx {
    public CxId Id { get; private set;}

    public class CxId {
        public string Id { get; private set;}

        public CxId(string id) {
            Id = id
        }
    }
}

public struct NonZero {
    int value;

    public NonZero(int value) {
        // check value is non-zero and throw if it is
    }
}

public class CxBalance {
    public uint Amount { get; private set; }

    //...
}

public CxBalance DoThing(CxId id, NonZero value);
```

This actually helps a lot!
* `id` has to be a `CxId`, not just any random string, so we know to start looking for API's that give us a `CxId`.
* `value` has to be `NonZero`, and we'll actually check that at runtime before ever getting here, so we can assume once we're calling this code that the actual value is not zero.
* The value returned is also related to the `Cx` in some way and probably has it's own methods and such.

Now if an agent or another programmer is coming a long, they have a lot more signposts in the code itself about what it does and how to use it... except it still requires a lot of context.  Let's look at just the function signature again:

```C#
public CxBalance DoThing(CxId id, NonZero value);
```
We still have unanswered questions:
* If I'm just reading this, I don't know if any of those types are passed by ref or by value.
* I don't know if those types can be null.
* I also don't know if any of the arguments are going to be modified, and I still don't know if `this` is going to be modified.
* I still don't know if this can throw exceptions.

As for that example with the fake id? I tried to fix it, but I can still do this:

```C#
foo.DoThing(new Cx.CxId("some random id"), new NonZero(1000));
```

Meaning I didn't actually prevent consumers of this API from passing in any values they want for id, I just guided them towards certain value types.
That problem is solvable, but it's actually really annoying and *ugly* in C# code... you can check out an actual way to do it below.

## Rust (Basic)

```rust
pub fn do_thing(&self, id: &str, value: u32) -> Result<u32, ThingError>;
```

Let's do our analysis again, what do we know from looking at this same function but in Rust:
* It's public.
* It's a method (it takes `&self` as it's first argument).
* It's a method that doesn't mutate `self`. (`&mut self` would show that we `self` can be mutated).
* It takes a reference to a string.
* It takes an integer value.
* None of it's arguments can be null, null isn't really a thing in Rust*.
    * **In safe Rust*.
* It can fail.
* If it fails, it returns a `ThingError`.
* If it doesn't, it returns an int.
* It's not asyncronous.

So already, we have more information right of the bat, and we should dive into some of that information that the programmer and the agent can use before we use some basic features in Rust to strengthen the API.

### Types

Rust only has `struct`, there's no special reference types.
If you want to pass a reference, you pass `&T` or `&mut T`.  When reading a type, you don't need more context as to whether that type is being passed by val or ref, it'll be very clear at the location you're passing it around.

As for mutability of a reference, well that has some special meaning and gives us much more information than C# was giving us.

In Rust, you can have any number of immutable references `&T`, or exactly one `&mut T` reference at a time.  This let's you know when you see either one whether or not you'll be able to mutate the value, and if you can, you'll know that no one else has access to that value until you're done with it.  Since the compiler enforces this, you and your agents don't need to make sure they aren't accidently sharing a reference in two places where it's mutated, the compiler will tell you for you.

#### Lifetimes

This rule doesn't just apply to simple function signatures either, it also applies to structs containing references, Rust will track the *lifetime* of a reference statically through your program, at compile time.

Let's look back at that C# definition real quick:

```C#
public CxBalance DoThing(CxId id, NonZero value);
```

Like I said before, we (and our agents) don't know whether those are reference or value types without more context. We (and our agents) also don't know if `this` is being mutated in this call.  Since we don't know either of those things, we *really* don't know if our arguments are going to be stored by `this` and kept alive or mutated by future calls.  If our code base is relying on that not being the case, some code can easily come and change that and cause a bug in a very different part of the codebase because we're sharing mutable access to a type.

What would happen if we tried to store that `&str` in `&self` in our Rust version?  Well first off, our comiler would tell us that we can't mutate `&self`:

```bash
error[E0594]: cannot assign to `self.id`, which is behind a `&` reference
  --> src/main.rs:13:9
   |
13 |         self.id = id;
   |         ^^^^^^^^^^^^ `self` is a `&` reference, so it cannot be written to
   |
help: consider changing this to be a mutable reference
   |
12 |     fn do_thing(&mut self, id: &str, value: u32) -> Result<u32, ThingError> {
   |
```

but let's say we fixed that, our compiler would *still* yell at us:

```bash
error: lifetime may not live long enough
  --> src/main.rs:13:9
   |
12 |     fn do_thing(&mut self, id: &str, value: u32) -> Result<u32, ThingError> {
   |                 ---------      - let's call the lifetime of this reference `'1`
   |                 |
   |                 has type `&mut Thing<'2>`
13 |         self.id = id;
   |         ^^^^^^^^^^^^ assignment requires that `'1` must outlive `'2`
```

What does this mean? It means we have a function taking two references, and we're trying to store one reference in the other, but we don't know how those two lifetimes relate!

We can fix this, how we fix it isn't super important for this post, but what is important is that the compiler is stopping us from doing something bad and making us clearly define how we want things to be related!

Once you clearly define it, it stops users of the API from misusing it, so you have a compiler backed rule that you give to your agents to follow.

### Option and Result

Rust doesn't have null values, and it doesn't have exceptions.

Instead, Rust has user definable `enum` types that are closed sets of related `struct`s.

For instance, that `Result<u32, ThingError>` is a built in `enum` defined like so:

```rust
pub enum Result<T, E> {
    Ok(T),
    Err(T)
}
```

Meaning any given instance of a `Result` can be either one of those two variants, never both. 

Instead of null values, we have `Option`, which is defined as:

```rust
pub enum Option<T> {
    Some(T),
    None
}
```

This means there's no guessing around exceptions or nullability, there's instead compiler checked handling of normal values reflected explicitly in your code:

```rust
let result = do_thing("test", 3);
match result {
    Ok(value) => {
        // handle ok case here
    },
    Err(err) => match err {
        ThingError::X => {/* handle error here */},
        ThingError::Y(data) => {/* handle error here */},
        ThingError::Z{
            struct_like,
            data,
            here
        } => {/* handle error here */}
    },
}
```

Everything you need to know is very local, and the compiler will remind you of the parts you forgot.

### Improvement

Let's improve our Rust API like we did for C# and see what we can improve:

```rust
mod cx {
    // I'm not going to explain Rust string handling and why this is String
    // when before we were using &str.  It's just too much for this post :)
    pub struct CxId(String);

    impl CxId {
        // No &self, self, or &mut self, so this is static
        // returns the type it's impled for, in our case CxId
        // public only to this module (rust default)
        fn new(id: String) -> Self {
            CxId(id)
        }
    }

    pub struct Cx {
        //...
        id: CxId,
    }

    impl Cx {
        pub fn new(id: String) -> Self {
            Self {
                //...,
                id: CxId::new(id)
            }
        }

        pub fn id(&self) -> &self {
            &self.id
        }
    }
}
use cx::{CxId, Cx};
use std::num::NonZero;

#[must_use]
pub fn do_thing(&self, id: &CxId, value: NonZero<u32>) -> Result<NonZero<u32>, ThingError>;
```

What have we improved? Well honestly? Not too much, the basic already gave us a lot more guarantees than C#, now all we've done is really solidified *how* you can use the API.

We did the same trick of moving id from a primitive weaker type to a strong domain specific type.  Rust also let us do hte trick of only getting `CxId` from `Cx` really easily and elegantly.  Since Rust visibility is module based and not classed based, we can define a module, have a type and it's method be public within the module, but private outside of it.  We can then use the private module methods within other methods that are public outside of the module so the `Cx` type and `CxId` types are public, but the only way to construct a `CxId` is through `Cx`.

Similarly to C#, we wrapped our integers in a `NonZero<T>` type, except in Rust this was provided to us by the standard lib.

We also did something similar to C#'s null analyzer by adding `#[must_use]` decorator.  All that does is tell the compiler to run an extra linter check to make sure any result we return from this function is used in someway, usually that means checking it or explicitly not checking it.  This isn't a rule in the language necessarily, but it is a compile time backed check.
