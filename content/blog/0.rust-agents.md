> I was going to give this as a talk for my larger product team at work, but decided to just write it down instead because I don't know how useful this will be and I don't think going over a bunch of code examples on a slideshow would be helpful for illustrating my point.

Well, AI coding has kind of taken over in the past few months; it's really unavoidable.  It's also a really good productivity booster... for the most part.

What I've found is that, while we can write code faster, reviewing code has become a huge bottleneck.

Of course, we can try to get rid of this bottleneck by having AI review the code as well, which we do, but I personally don't think that gets rid of the bottleneck.
It can just push the review from the engineer's job to the customer's job when they find a bug caused by:

1. An unclear prompt...
2. Leading to an assumption by the agent...
3. Writing code implementing this assumed behavior or restriction...
4. With good test coverage and clear documentation...
5. That passes AI code reviews because it works...
6. That has not actually been looked at by the engineer to confirm it didn't do anything weird.

A careful human review can catch this sort of situation by *reading the code* the agent writes... except reading code is really hard!
Part of what makes code easier to understand is writing code and being forced to understand the surrounding context of the code you're writing, but as we move towards less of the writing part, the reading part becomes increasingly more difficult.  To add to that difficulty... AI writes a lot of code very quickly, and while my team has found it incredibly useful for getting longstanding and important refactors and fixes out of the way, the reason those issues were longstanding is that they would require a huge PR, and we still want to be able to review that big PR!

So, if we work backwards, what we want is some sort of tool, process, mindset, etc. that makes reviewing PRs easier, makes PRs smaller, makes agents assume less from an unclear prompt, or makes prompts clearer.

And we actually do have a tool for that: the programming language you use! Even though this post is about Rust, your programming language of choice offers a lot of tools to encode your intentions and guardrails into the code you or someone else (someone here being more of a something... still haunted by seeing an agent's comment addressing me as a *human* programmer...) will have to abide by.

The tools available don't just let you define intention better, leading to more correct code, they can also tighten the feedback cycle by catching mistakes before we ever run the code.  Before I actually go into the tools and how/why we should use them (and ultimately why I think Rust is our best language available), let's go over those feedback loops:

* Coding -> Compiling -> Testing -> Running -> Releasing
    * This is our slowest feedback loop, and the one we really don't want to see an error in.  If we see an error here, it means a customer spotted it (which makes us look bad and, as a customer myself, is very annoying) or will spot it.  If we see an error here, we have to go through a bit of exploratory work to figure out what actually caused it, which requires a lot of code exploration usually.  It also means to fix the error, we have to go through the whole release process again.
* Coding -> Compiling -> Testing -> Running
    * This is your local debugging feedback loop.  It's very open-ended, which is good, but ideally if you're discovering a bug here, you're going to wish you discovered it earlier.  It is still a relatively slow feedback loop as each bug you find requires both running the code (entailing any setup cost required to do so) and exploring well enough to find a bug.  When we do find a bug, it also requires a similar amount of code exploration to narrow down the issue.
* Coding -> Compiling -> Testing
    * We love this feedback loop.  It's reasonably quick (if you wrote your tests to run very quickly (you should write your tests to run very quickly)) and a very focused guardrail for specific behaviors and constraints.  If a test fails, there's usually going to be a pretty narrow scope of the code that can cause it to fail.  One issue is that tests can grow large and complex as the features they are testing grow, so writing/maintaining/***reading*** them becomes a pain.
* Coding -> Compiling
    * This is the loop we love.  This is the loop your agents love.  When the compiler catches a bug, it usually tells us where to look and what rule we've broken.  We don't even have to run the code to find it!

The rest of this post is going to discuss tools that let us move some errors from the end of the feedback chain all the way to the beginning: tools that let us write intention and restriction as code and not just as a prompt.  The tools are simple and we've had them this whole time.  Just because our computers are now able to read and act on plain text much better than before, it doesn't mean they stopped being computers that can read and act on programming languages deterministically, so we should really be using *type systems and static analysis* to better guide our agents.

# Type Systems and Static Analysis

Our type systems let us turn our code from just a process into a contract, and static analyzers + extensible static analysis systems let us add our own extra rules and restrictions for feedback during development and builds.

## C# (Basic)

Let's look at this C# method and try to figure out what the signature is telling the reader, whether that's us or an agent:

```csharp
public uint DoThing(string id, uint value);
```

Well... here's what we know:
* This is an instance method.
* It returns a nonnegative integer.
* It takes a string `id` argument and some nonnegative integer `value` argument.
* It allegedly *does thing*.
* It is public.
* It's not marked `async`.

Now what are the things we don't know from looking at it:
* What exactly is `id`, and what IDs are okay? Is it correct to put any string there?
* What values are okay, is anything okay?
* Is this method going to modify `this` in some way?
    * It could modify it.
    * It could also just read information from it.
    * If it's a struct we could mark the method `readonly`, but not for classes.
* Can this method fail? Does it throw exceptions? What exceptions can it throw?

So what we have here is a method that uses its name, and argument names, to tell us its intention, to **do thing**, but it hasn't communicated what restrictions we have when doing thing.  We know we can do it, but we don't know how, when, or why.

Is this valid?

```csharp
foo.DoThing("some random id", 1000);
```

Maybe... so let's use some simple typing to start turning this into a contract we have to follow:

```csharp
#nullable enable

public class Cx {
    public Cx(string id) => Id = new CxId(id);

    public CxId Id { get; private set; }

    public sealed class CxId {
        public string Id { get; }

        public CxId(string id) {
            Id = id;
        }
    }
}

public sealed class NonZero {
    public uint Value { get; }

    public NonZero(uint value) {
        if (value == 0)
            throw new ArgumentOutOfRangeException(nameof(value));

        Value = value;
    }
}

public class CxBalance {
    public uint Amount { get; private set; }

    //...
}

public CxBalance DoThing(Cx.CxId id, NonZero value);
```

This actually helps a lot!
* `id` has to be a `CxId`, not just any random string, so we know to start looking for APIs that give us a `CxId`.
* `value` has to be `NonZero`, and its constructor checks the value at runtime before we get here.  Any instance constructed that way holds a nonzero value.
* The value returned is also related to the `Cx` in some way and probably has its own methods and such.

Now if an agent or another programmer is coming along, they have a lot more signposts in the code itself about what it does and how to use it... except it still requires a lot of context.  Let's look at just the function signature again:

```csharp
public CxBalance DoThing(Cx.CxId id, NonZero value);
```
We still have unanswered questions:
* Without checking the type definitions, I don't know whether these arguments are copies of structs or references to shared objects.
* Can I actually rely on those references not being null?
* I also don't know if any of the arguments are going to be modified, and I still don't know if `this` is going to be modified.
* I still don't know if this can throw exceptions.

As for that example with the fake id? I tried to fix it, but I can still do this:

```csharp
foo.DoThing(new Cx.CxId("some random id"), new NonZero(1000));
```

Meaning I didn't actually prevent consumers of this API from passing in any values they want for id, I just guided them towards certain value types.
That problem is solvable, but it's actually really annoying and *ugly* in C# code... you can check out an actual way to do it below.

<details>
<summary>A C# factory with a stricter construction boundary</summary>

```csharp
#nullable enable

using System;
using System.Runtime.CompilerServices;

public class Cx
{
    public sealed class CxId
    {
        private CxId(string id) => Id = id;

        // This lambda can call the private constructor because it is defined in CxId.
        static CxId() => _createId = id => new CxId(id);

        public string Id { get; }
    }

    private static Func<string, CxId> _createId = null!;

    // Initialize CxId before Cx's instance constructor uses the factory.
    static Cx() =>
        RuntimeHelpers.RunClassConstructor(typeof(CxId).TypeHandle);

    private static CxId CreateId(string id) => _createId(id);

    public Cx(string id) => Id = CreateId(id);

    public CxId Id { get; private set; }
}
```
This is not simple or straightforward C# code.

</details>

So, now we do have a better API that is harder to misuse, but it's one that a human or agent still needs a lot of context to use correctly, and still has some open ends to be used incorrectly, with probably the biggest hole being what errors to handle and how to handle them as well as what values can this method actually change?

In our feedback loop, we always have to write the code and compile it, but with this API we still need to read the implementation or documentation to figure out what errors to handle, and write tests for them.  For a more complex API, we'll probably also need some guards or tests to make sure only the values we think we can change or want to change are being changed.

### Nullability and analyzers

Oh, and what about null?  C# has tools for that too!  That `#nullable enable` in our stronger API turns on nullable reference type annotations and warnings.  Now `CxId`, `NonZero`, and `CxBalance` say we don't expect null, and the compiler can warn when we pass or return something that might be null.  If returning no balance was allowed, we'd write `CxBalance?` instead.

We can also give the analyzer more information than just "this can be null."  Say we added a lookup method:

```csharp
#nullable enable
using System.Diagnostics.CodeAnalysis;

public bool TryGetId(string name, [NotNullWhen(true)] out Cx.CxId? id);
```

The `?` says `id` might be null, but `[NotNullWhen(true)]` tells the compiler that if this method returns true, `id` won't be null.  So our agent can write:

```csharp
if (foo.TryGetId("some name", out var id)) {
    foo.DoThing(id, new NonZero(1000));
}
```

And the compiler knows we checked!  We don't have to make the agent guess what a successful lookup means for that argument.

This catches a lot of mistakes, but it's static analysis, not a runtime guarantee.  It uses types and follows the code's control flow, but `CxId` and `CxId?` are still the same runtime type.  Code that hasn't opted in can still pass us null without those warnings, and `!` can silence a warning without actually checking anything.  We can make nullable warnings fail the build, but that still doesn't make null impossible.

And we can write our own Roslyn analyzers too!  If an agent keeps making the same mistake, instead of writing another skill asking it not to do that, we can try writing an analyzer that spots the pattern and reports it during the build.  Now both the engineer and the agent get feedback in that short compile loop.  A skill asks the agent to remember a rule; an analyzer checks whether it followed it.

This was a lot of text and analysis for a very simple API, and it's probably overboard, but still illustrative of all the things to think about in a very very simple method call.  The language helps a little, but we have to really work to have it help us, and even then it still leaves us with things to infer.  Can Rust, the actual thing I want to talk about, do better?

## Rust (Basic)

```rust
pub fn do_thing(&self, id: &str, value: u32) -> Result<u32, ThingError>;
```

Let's do our analysis again, what do we know from looking at this same function but in Rust:
* It's public.
* It's a method (it takes `&self` as its first argument).
* It borrows `self` through a shared reference.  (`&mut self` would let it mutate ordinary fields.)
* It takes a reference to a string slice.
* It takes an unsigned integer by value.
* None of its arguments can be null in safe Rust.
* It can return an error.
* If it returns an error, we get a `ThingError`.
* If it succeeds, we get an unsigned integer.
* It's not marked `async`.

So already, we have more information right off the bat, and we should dive into some of that information that the programmer and the agent can use before we use some basic features in Rust to strengthen the API.

### Types

Rust doesn't have C#'s implicit class-versus-struct distinction.  If you want to borrow a value, you pass `&T` or `&mut T`.  In both languages the value being passed can be a reference, but in Rust the borrowing rules are right there in the signature.  We don't need to go look up the type to find them.

As for mutability of a reference, well that has some special meaning and gives us much more information than C# was giving us.

In Rust, you can have multiple shared references `&T`, or an exclusive `&mut T` reference to the same data, but not conflicting uses of both.  This lets you know whether you can mutate ordinary fields, and if you can, that no one else can use a conflicting reference while you're doing it.  Since the compiler enforces this, you and your agents don't need to make sure you aren't accidentally sharing conflicting access, the compiler will tell you for you.

#### Lifetimes

This rule doesn't just apply to simple function signatures either; it also applies to structs containing references.  Rust checks the *lifetimes* of those references statically, at compile time.

Let's look back at that C# definition real quick:

```csharp
public CxBalance DoThing(Cx.CxId id, NonZero value);
```

Like I said before, we (and our agents) don't know whether those are reference or value types without more context. We (and our agents) also don't know if `this` is being mutated in this call.  If an argument refers to a mutable object, the signature doesn't tell us whether the receiver retains it and mutates it later.  If our codebase is relying on that not being the case, an implementation change can cause a bug in a very different part of the codebase because we're sharing mutable access to an object.

What would happen if we tried to store that `&str` in an `id` field on our Rust type?  Well first off, our compiler would tell us that we can't assign to that field through `&self`:

```bash
error[E0594]: cannot assign to `self.id`, which is behind a `&` reference
  --> src/main.rs:13:9
   |
13 |         self.id = id;
   |         ^^^^^^^^^^^^ `self` is a `&` reference, so it cannot be written to
   |
help: consider changing this to be a mutable reference
   |
12 |     fn do_thing(&mut self, id: &str, value: u32) -> Result<u32, ThingError> {
   |
```

but let's say we fixed that, our compiler would *still* yell at us:

```bash
error: lifetime may not live long enough
  --> src/main.rs:13:9
   |
12 |     fn do_thing(&mut self, id: &str, value: u32) -> Result<u32, ThingError> {
   |                 ---------      - let's call the lifetime of this reference `'1`
   |                 |
   |                 has type `&mut Thing<'2>`
13 |         self.id = id;
   |         ^^^^^^^^^^^^ assignment requires that `'1` must outlive `'2`
```

What does this mean? It means we have a function taking two references, and we're trying to store one in the other, but we haven't said how long that stored reference needs to stay valid!

We can fix this, how we fix it isn't super important for this post, but what is important is that the compiler is stopping us from doing something bad and making us clearly define how we want things to be related!

Once you clearly define it, the compiler checks that the stored reference can't outlive its data, so you have a compiler-backed rule about how long data is valid for that your agents have no choice but to follow.

### Option and Result

Rust references can't be null, and Rust uses `Result` instead of exceptions for ordinary errors.

Instead, Rust has user-defined `enum` types: a fixed set of named variants, each of which can optionally carry data.

For instance, that `Result<u32, ThingError>` uses a standard-library `enum` defined like so:

```rust
pub enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

Meaning any given instance of a `Result` can be either one of those two variants, never both.

Instead of null values, we have `Option`, which is defined as:

```rust
pub enum Option<T> {
    Some(T),
    None,
}
```

This means the errors and missing values we want callers to handle are right there in the types:

```rust
let result = thing.do_thing("test", 3);
match result {
    Ok(value) => {
        // handle ok case here
    },
    Err(err) => match err {
        ThingError::X => {/* handle error here */},
        ThingError::Y(data) => {/* handle error here */},
        ThingError::Z{
            struct_like,
            data,
            here
        } => {/* handle error here */}
    },
}
```

Everything we need to handle here is local, and the compiler will remind us of the variants we forgot.  Add a new error variant?  Unless we've used a catch-all, the compiler will point out the callers that need to handle it!

*Rust can still panic, so `Result` doesn't mean every possible failure is covered. But a panic is for a non-recoverable error, not normal error handling.*

### Improvement

Let's improve our Rust API like we did for C# and see what we can improve:

```rust
mod cx {
    // I'm not going to explain Rust string handling and why this is String
    // when before we were using &str.  It's just too much for this post :)
    pub struct CxId(String);

    impl CxId {
        // An associated function: no receiver, and Self means CxId.
        // Private to this module and its descendants by default.
        fn new(id: String) -> Self {
            CxId(id)
        }
    }

    pub struct Cx {
        //...
        id: CxId,
    }

    impl Cx {
        pub fn new(id: String) -> Self {
            Self {
                //...,
                id: CxId::new(id)
            }
        }

        pub fn id(&self) -> &CxId {
            &self.id
        }
    }
}
pub use cx::{CxId, Cx};
```

With these types, our method signature becomes:

```rust
pub fn do_thing(&self, id: &CxId, value: NonZero<u32>) -> Result<NonZero<u32>, ThingError>;
```

Here, `NonZero` comes from `std::num::NonZero`.

What have we improved? Well honestly? Not too much, the basic version already gave us a lot more guarantees than C#, now all we've done is really solidified *which values* you can use with the API.

We did the same trick of moving `id` from a primitive weaker type to a strong domain-specific type.  Rust also let us do the trick of only getting `CxId` from `Cx` really easily and elegantly.  Since Rust visibility is module-based and not class-based, we can keep construction private to the module while making `Cx` and `CxId` public.  Code outside that module gets its `CxId` through `Cx`.

That doesn't validate the string itself, but it gives us a place to do that validation without callers bypassing it.

Similarly to C#, we wrapped our integers in a nonzero type, except in Rust `NonZero<u32>` is provided by the standard library.

`Result` also already has the `#[must_use]` attribute.  That tells the compiler to warn if we ignore the result, so an agent gets another reminder to handle it.  We can still explicitly discard it, but we have to say that's what we're doing.

# Conclusion

This doesn't make Rust free of tradeoffs.  Borrowing constraints can require API redesign, the learning curve is real, and the total task might still take longer.  But the difference isn't just how much checking is enabled by default.  C# can encode useful domain rules, but it doesn't offer equivalent type-system contracts for ordinary reference lifetimes, shared versus exclusive borrowing, or exhaustive matching over Rust-style data-carrying enums.  Rust lets us express and enforce constraints that C# API design alone can't reproduce, giving an agent information it would otherwise have to reconstruct from implementation details or documentation.
